# 구현 내용

## 패키지 구조

```text
notificationdeliverysystem
├── domain
│   ├── notification
│   └── outbox
├── application
│   └── notification
│       ├── provided
│       └── required
└── adapter
    ├── webapi
    ├── persistence
    ├── messaging
    │   ├── kafka
    │   └── outbox
    └── integration
```

## 주요 컴포넌트

### Web API

- `NotificationApi`
  - `POST /notifications` 요청을 받는다.
  - `NotificationRegister` provided port에 위임한다.
- `ApiControllerAdvice`
  - validation 실패와 도메인 예외를 `ProblemDetail` 응답으로 변환한다.

### Application

- `NotificationRegister`
  - 알림 등록 유스케이스 진입 포트다.
- `NotificationSender`
  - Kafka Consumer가 호출하는 발송 유스케이스 진입 포트다.
- `NotificationRegisterService`
  - 등록 유스케이스를 조율한다.
  - `requestId` 중복 확인 후 신규 등록 또는 기존 알림 반환을 결정한다.
- `NotificationDispatchService`
  - 단건 알림 발송 실행 유스케이스를 담당한다.
  - 완료 상태를 먼저 확인하고, 미완료 알림만 `DispatchLockManager`로 락 획득을 시도한다.
  - 발송 처리 안에서 `PENDING -> PROCESSING -> SENT/FAILED` 상태 전이를 수행한다.
- `NotificationOutboxPublishService`
  - `PENDING` Outbox 이벤트를 Kafka publisher port로 발행한다.
  - Kafka 발행 전 Outbox 이벤트를 `PROCESSING`으로 변경한다.
  - Kafka 발행 실패 시 Outbox 이벤트를 다시 `PENDING`으로 되돌린다.
  - Kafka 발행은 DB 트랜잭션 밖에서 수행한다.
- `NotificationOutboxRecoverService`
  - 오래된 `PROCESSING` Outbox 이벤트를 `PENDING`으로 되돌린다.
- `NotificationOutboxQueryService`
  - Outbox 발행에 필요한 조회를 read-only 트랜잭션으로 처리한다.
- `NotificationOutboxModifyService`
  - Outbox 이벤트 상태를 `PROCESSING`, `PUBLISHED`, `PENDING`으로 변경한다.

### Domain

- `Notification`
  - 단건 알림 요청과 발송 상태를 가진다.
- `RequestId`
  - 클라이언트 retry 중복 판단에 사용하는 값 객체다.
- `OutboxEvent`
  - Kafka 발행 예정 이벤트다.
  - `status, id` 인덱스로 polling 조회를 보조한다.
  - `aggregateType, aggregateId, status` 인덱스로 commit 이후 즉시 발행 단건 조회를 보조한다.

### Persistence

- `NotificationRepository`, `OutboxEventRepository`
  - application required port다.
  - Spring Data 타입을 상속하지 않는 순수 인터페이스다.
- `NotificationJpaRepository`, `OutboxEventJpaRepository`
  - Spring Data JPA 전용 repository다.
  - `adapter.persistence` 내부에서만 사용한다.
- `NotificationPersistenceAdapter`, `OutboxEventPersistenceAdapter`
  - required port 구현체다.
  - application 서비스가 JPA 구현체를 직접 알지 않게 감싼다.

### Dispatch Lock

- `DispatchLockManager`
  - application required port다.
  - 같은 알림의 동시 외부 발송을 막기 위한 락 획득 기능을 추상화한다.
- `DispatchLock`
  - try-with-resources로 락 해제를 보장하기 위한 락 핸들이다.
- `RedisDispatchLockManager`
  - Redis `SET NX PX` 방식으로 `dispatch-lock:{notificationId}` 락을 획득한다.
  - 락 해제 시 Lua script로 소유자 토큰을 비교한 뒤 삭제한다.
  - `notification.dispatch-lock.type=redis`일 때 활성화된다.
- `DummyDispatchLockManager`
  - Redis 없이 로컬 기본 실행을 가능하게 하는 대체 구현이다.
  - 실제 동시 중복 발송 방지는 하지 않는다.

### Messaging

- `NotificationKafkaProducer`
  - `NotificationMessagePublisher` required port 구현체다.
  - Kafka topic `single-notification-send`로 메시지를 발행한다.
  - `notification.kafka.publish-timeout-ms` 안에 broker ack를 받지 못하면 발행 실패로 처리한다.
- `NotificationKafkaConsumer`
  - Kafka 메시지를 소비해 `NotificationSender.send(notificationId)`를 호출한다.
  - `notification.role.worker-enabled=true`일 때 활성화된다.
- `NotificationOutboxEventListener`
  - `@TransactionalEventListener(AFTER_COMMIT)`로 Outbox 저장 이벤트를 받는다.
  - commit 이후 즉시 Kafka 발행을 시도한다.
- `NotificationOutboxPoller`
  - 남아 있는 `PENDING` Outbox 이벤트를 주기적으로 재처리한다.
  - `notification.outbox.publisher-enabled=true`일 때 활성화된다.
- `NotificationOutboxRecoveryPoller`
  - 오래된 `PROCESSING` Outbox 이벤트를 주기적으로 복구한다.
  - 발행 polling과 별도 주기, 별도 batch size로 실행된다.

### Mock Send API Adapter

- `MockNotificationSenderRouter`
  - `ExternalNotificationSender` required port 구현체다.
- `EmailMockSender`, `SmsMockSender`, `KakaoMockSender`
  - 채널별 Sender 구현체다.
  - 공통 추상 클래스 `AbstractMockChannelSender`를 상속한다.
- `MockSendApiClient`
  - 실제 외부 API처럼 동작하는 로컬 Mock Send API를 HTTP로 호출한다.

## Week2 구현 진행 구조

Week2에서는 로그 기반 Mock Sender를 실제 HTTP Mock Send API 호출 구조로 교체했다.
Mock API 프로젝트는 로컬의 `/Users/ogu/study/과제전형 5기/알림발송시스템/sendmock`를 사용한다.

### Mock Send API Adapter

- `MockNotificationSenderRouter`
  - `ExternalNotificationSender` required port 구현체다.
- `EmailMockSender`, `SmsMockSender`, `KakaoMockSender`
  - 채널별 발송 구현체다.
- `AbstractMockChannelSender`
  - 채널별 Sender의 공통 발송 흐름을 가진다.
- `MockSendApiClient`
  - `POST http://localhost:8081/mock/send`로 발송 요청을 보낸다.
  - 요청에는 `requestId`, `channelType`, `receiver`, `message`, `metadata.notificationId`를 담는다.
  - connect timeout과 read timeout을 명시한다.
  - 응답 status code와 body를 해석해 성공, 재시도 가능 실패, 재시도 불가능 실패로 분류한다.

### 발송 실패 분류

- `2xx`: `SENT`
- 일반 `4xx`: `FAILED`
- `429`: `RETRY_WAIT`
- `5xx`: `RETRY_WAIT`
- connect timeout, read timeout: `RETRY_WAIT`
- 응답 파싱 실패: `FAILED`

### 재처리 Poller

- `NotificationRetryPoller`
  - `RETRY_WAIT` 상태이고 `nextRetryAt`이 지난 알림을 제한 조회한다.
  - 조회한 알림을 기존 단건 알림 발송 토픽으로 다시 발행한다.
  - 발송 유스케이스에서 재시도 한도를 초과한 알림은 `DEAD`로 전환한다.
  - Week2 1차 구현은 Kafka retry topic이나 DLQ topic 대신 DB 상태 기반 재처리 poller를 사용한다.

### 상태 추적

Week2에서는 알림 상태를 `PENDING`, `PROCESSING`, `SENT`, `RETRY_WAIT`, `FAILED`, `DEAD`로 확장한다.
기존 `SENDING`은 Consumer 처리 중이라는 의미가 더 명확한 `PROCESSING`으로 변경했다.

실패 추적을 위해 `retryCount`, `lastError`, `lastErrorCode`, `lastExternalStatusCode`, `lastFailedAt`, `nextRetryAt`을 저장한다.
상세 설계는 `docs/week2-발송보장과재처리.md`를 따른다.

## Outbox 발행 흐름

```text
NotificationRegisterService.register()
 -> Notification 저장
 -> OutboxEvent 저장
 -> OutboxEventNotifier.notifyOutboxSaved(notificationId)
 -> 202 Accepted

Spring transaction commit
 -> NotificationOutboxEventListener.publishAfterCommit()
 -> NotificationOutboxPublishService.publishPendingByNotificationId()
 -> OutboxEvent.startPublishing()
 -> Kafka 발행
 -> OutboxEvent.markPublished()
```

즉시 발행이 실패하면 listener는 예외를 전파하지 않는다.
이벤트는 `PROCESSING`에서 `PENDING`으로 돌아가고 polling publisher가 다시 처리한다.

```text
NotificationOutboxPoller
 -> PENDING OutboxEvent batch 조회
 -> PROCESSING 변경
 -> Kafka 발행
 -> PUBLISHED 변경
```

```text
NotificationOutboxRecoveryPoller
 -> 오래된 PROCESSING OutboxEvent batch 조회
 -> PENDING 변경
```

## Outbox 조회 방식

polling publisher는 전체 Outbox 테이블을 매번 읽지 않는다.

```text
status = PENDING
order by id asc
limit polling-batch-size
```

현재 기본 batch size는 100이다.

```yaml
notification:
  outbox:
    polling-batch-size: 100
    recovery-batch-size: 500
    recovery-interval-ms: 30000
    processing-timeout-ms: 300000
  dispatch-lock:
    type: dummy
    ttl-ms: 30000
```

조회 성능을 위해 `OutboxEvent`에는 다음 인덱스를 둔다.

| 인덱스 | 용도 |
| --- | --- |
| `status, id` | `PENDING` 이벤트를 id 순서로 제한 조회 |
| `status, updatedAt` | 오래된 `PROCESSING` 이벤트 timeout 복구 조회 |
| `aggregateType, aggregateId, status` | commit 이후 즉시 발행 대상 단건 조회 |

## 역할 분리 설정

```yaml
notification:
  role:
    api-enabled: true
    worker-enabled: false
  outbox:
    publisher-enabled: false
```

- API 역할: Web API, DB 저장, Outbox 저장
- Outbox Publisher 역할: commit 이후 즉시 발행, 미발행 이벤트 polling
- Worker 역할: Kafka Consumer, Mock Sender

아직 단일 애플리케이션 안에서 실행하지만, 나중에 API 서버와 Worker 서버로 나누기 위한 전제만 둔다.
