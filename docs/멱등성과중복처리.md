# 멱등성과 중복 처리

알림 발송 시스템은 API 요청 저장, Outbox 발행, Kafka 소비, 외부 발송으로 이어진다.
각 단계에서 생기는 중복의 성격이 다르므로 하나의 키로 모든 중복을 해결하지 않는다.
단계별 목적에 맞는 식별자를 분리해서 사용한다.

## 핵심 식별자

| 식별자 | 의미 | 주요 사용 위치 |
| --- | --- | --- |
| `requestId` | 클라이언트가 같은 발송 의도를 식별하기 위해 전달하는 요청 ID | API 등록 중복 방지, 외부 발송 API의 `Idempotency-Key` 후보 |
| `notificationId` | 서버 DB에 생성된 단건 알림의 ID | Kafka record key, Consumer 발송 처리 대상, Redis 발송 락 키 |
| `OutboxEvent.id` | Outbox 이벤트 row 자체의 ID | Outbox polling 대상 구분, 이벤트 추적 |

`OutboxEvent.id`는 알림 ID가 아니다.
따라서 외부 발송 멱등성 키로 사용하지 않는다.

## 중복이 생기는 위치

### 1. API 등록 중복

클라이언트가 네트워크 오류나 타임아웃 때문에 같은 요청을 다시 보낼 수 있다.
이 경우 같은 `requestId`는 같은 발송 의도로 본다.

현재 구현은 `requestId`에 unique 제약을 두고, 이미 저장된 알림이 있으면 기존 알림을 반환한다.
동시에 같은 `requestId` 요청이 들어오면 두 요청 모두 처음 조회에서 없다고 볼 수 있다.
이때 한쪽 insert가 먼저 성공하고 다른 한쪽은 unique 제약 위반이 발생할 수 있다.

이 경우 저장에 실패한 트랜잭션에서 바로 복구 조회를 이어가면 rollback-only 상태의 영향을 받을 수 있다.
그래서 실패한 저장 트랜잭션이 롤백된 뒤, 분리된 조회 트랜잭션으로 기존 알림을 다시 찾아 순차 중복 요청과 동시 중복 요청의 API 응답을 맞춘다.

```mermaid
sequenceDiagram
    autonumber
    participant ClientA as Client A
    participant ClientB as Client B
    participant ServiceA as Register Service A
    participant ServiceB as Register Service B
    participant DB as DB

    ClientA->>ServiceA: POST requestId=req-001
    ClientB->>ServiceB: POST requestId=req-001

    ServiceA->>DB: requestId=req-001 조회
    DB-->>ServiceA: 없음
    ServiceB->>DB: requestId=req-001 조회
    DB-->>ServiceB: 없음

    ServiceA->>DB: Notification insert
    DB-->>ServiceA: 성공
    ServiceA->>DB: OutboxEvent insert
    ServiceA-->>ClientA: 202 Accepted notificationId=10

    ServiceB->>DB: Notification insert
    DB-->>ServiceB: unique 제약 위반
    ServiceB->>ServiceB: 저장 트랜잭션 롤백
    ServiceB->>DB: requestId=req-001 재조회
    DB-->>ServiceB: notificationId=10
    ServiceB-->>ClientB: 202 Accepted notificationId=10
```

#### rollback-only 처리 기준

`DataIntegrityViolationException`은 DB unique 제약 위반처럼 트랜잭션 안의 쓰기 작업이 실패했을 때 발생한다.
이 예외가 발생한 트랜잭션은 rollback-only로 표시되거나 Hibernate 세션이 실패 상태가 될 수 있다.
그 상태에서 같은 트랜잭션으로 조회를 이어가면 기존 row를 찾는 코드가 있어도 트랜잭션 종료 시점에 예외가 다시 발생할 수 있다.

현재 등록 유스케이스의 바깥 메서드인 `NotificationRegisterService.register()`에는 `@Transactional`을 붙이지 않는다.
저장은 `NotificationRegisterTransactionService.registerNewNotification()` 안의 트랜잭션으로만 수행한다.
따라서 unique 충돌이 발생하면 저장 트랜잭션은 메서드 밖으로 빠져나오면서 롤백되고, 이후 `findByRequestId()` 호출은 별도 조회 트랜잭션에서 실행된다.

이 구조에서는 충돌 복구 조회에 `REQUIRES_NEW`를 당장 명시하지 않아도 된다.
다만 나중에 `NotificationRegisterService.register()` 같은 바깥 유스케이스 메서드에 `@Transactional`을 붙인다면, 저장 실패 트랜잭션과 복구 조회 트랜잭션이 다시 섞일 수 있다.
그때는 `findExistingNotificationAfterRequestIdCollision()`처럼 복구 조회 전용 메서드를 만들고 `REQUIRES_NEW`를 명시하는 방식으로 바꾸는 것이 안전하다.

### 2. Outbox 이벤트 중복

Outbox 이벤트는 "알림이 생성되었으니 메시지 브로커로 발행해야 한다"는 작업 기록이다.
현재 `aggregateType + aggregateId + status` 인덱스는 조회 성능을 위한 인덱스이며 unique 제약은 아니다.

현재 서비스 흐름에서는 알림 생성과 Outbox 생성을 한 트랜잭션에서 한 번만 수행한다.
나중에 같은 알림에 대해 같은 종류의 PENDING Outbox 이벤트가 여러 개 생길 가능성까지 DB에서 막고 싶다면 `aggregateType + aggregateId + eventType` 기준 unique 제약을 검토한다.

현재 `SINGLE_NOTIFICATION_SEND`는 "이 알림을 한 번 발송하라"는 명령성 작업 이벤트다.
이 의미만 보면 같은 `aggregateType + aggregateId + eventType` 조합을 unique로 막는 편이 자연스럽다.
다만 아직 이벤트 타입이 하나뿐이고, 등록 서비스 흐름에서 Outbox를 한 번만 만들고 있으므로 1단계에서는 DB 제약을 추가하지 않는다.

나중에 같은 알림에 같은 eventType이 여러 번 생겨야 하는 요구사항이 생길 수도 있다.
예를 들어 `DELIVERY_ATTEMPT`가 "발송 시도 1회"를 의미한다면 같은 알림에 여러 row가 생기는 것이 맞다.
반대로 `SINGLE_NOTIFICATION_SEND_REQUESTED`처럼 "발송 요청 작업"을 의미한다면 중복 생성을 막는 것이 맞다.
따라서 Outbox unique 제약은 이벤트 타입의 의미가 더 늘어난 뒤 함께 결정한다.

### 3. Kafka 메시지 중복

Outbox publisher는 PENDING 이벤트를 PROCESSING으로 바꾼 뒤 Kafka로 발행하고, broker ack를 받은 뒤 Outbox 상태를 PUBLISHED로 변경한다.
하지만 Kafka 발행은 DB 트랜잭션 밖의 외부 시스템 효과다.
Kafka 발행 성공 후 상태 저장이 실패하면 Kafka에는 메시지가 이미 들어갔지만 Outbox는 다시 PENDING으로 돌아가거나 PROCESSING에 남을 수 있다.

`PENDING`으로 돌아간 이벤트는 현재 polling publisher가 다시 조회해 재발행한다.
반대로 애플리케이션이 `PROCESSING` 상태로 바꾼 뒤 종료되면 catch 블록이 실행되지 못하므로 이벤트가 `PROCESSING`에 남을 수 있다.
현재 발행 polling 조회는 `PENDING`만 대상으로 한다.
그래서 복구 poller가 오래된 `PROCESSING` 이벤트를 다시 `PENDING`으로 되돌린다.
발행 poller와 복구 poller는 별도 주기와 별도 batch size로 실행한다.

이후 polling publisher가 같은 이벤트를 다시 발행하면 Kafka에는 같은 알림 메시지가 한 번 더 들어간다.
이것은 Outbox 패턴에서 흔한 at-least-once 특성이다.
정확히 한 번만 발행되는 것을 전제로 두지 않고, Consumer와 외부 발송 단계에서 중복을 견디게 만든다.

```mermaid
sequenceDiagram
    autonumber
    participant Poller as Outbox Publisher
    participant Kafka as Kafka
    participant DB as DB
    participant Consumer as Consumer

    Poller->>DB: PENDING OutboxEvent 조회
    DB-->>Poller: OutboxEvent id=55, notificationId=10
    Poller->>Kafka: notificationId=10 발행
    Kafka-->>Poller: broker ack
    Poller->>DB: OutboxEvent PUBLISHED 저장
    DB--xPoller: commit 실패

    Poller->>DB: PENDING OutboxEvent 재조회
    DB-->>Poller: OutboxEvent id=55, notificationId=10
    Poller->>Kafka: notificationId=10 재발행

    Kafka-->>Consumer: notificationId=10
    Kafka-->>Consumer: notificationId=10
```

### 4. 외부 발송 중복

Kafka에 같은 `notificationId` 메시지가 여러 번 들어가면 Consumer도 같은 알림을 여러 번 받을 수 있다.
시간차가 있는 중복은 알림 상태가 이미 `SENT`, `FAILED`, `DEAD`인지 확인해서 건너뛸 수 있다.

문제는 거의 동시에 같은 메시지를 여러 Consumer가 처리하는 경우다.
두 Consumer가 모두 아직 발송 전 상태를 보고 외부 발송 API를 호출하면 실제 알림이 두 번 발송될 수 있다.

이 단계에서는 `dispatch-lock:{notificationId}` 형태의 Redis 분산락을 사용한다.
같은 알림 ID를 처리하는 Consumer 중 하나만 외부 발송 직전 구간에 들어가게 하는 목적이다.
락은 Kafka 중복 발행 자체를 막는 장치가 아니라, 중복 메시지가 들어와도 실제 발송이 동시에 실행되지 않게 막는 장치다.
락에는 TTL을 둔다.
Consumer가 락을 잡은 뒤 프로세스가 종료되면 직접 락을 해제하지 못하므로, TTL 없이 두면 같은 알림이 영원히 처리되지 않을 수 있기 때문이다.

TTL은 외부 발송 timeout보다 충분히 길게 잡아야 한다.
처리 시간이 TTL보다 길어지면 락이 먼저 만료되고 다른 Consumer가 같은 알림 락을 다시 잡을 수 있다.
이 경우 Redis 락만으로는 중복 발송을 완전히 막지 못하므로, DB 상태 체크와 외부 발송 API의 idempotency key를 함께 사용해야 한다.

```mermaid
sequenceDiagram
    autonumber
    participant Kafka as Kafka
    participant ConsumerA as Consumer A
    participant ConsumerB as Consumer B
    participant Redis as Redis
    participant Sender as External Sender
    participant DB as DB

    Kafka-->>ConsumerA: notificationId=10
    Kafka-->>ConsumerB: notificationId=10

    ConsumerA->>DB: Notification 10 조회
    DB-->>ConsumerA: PENDING
    ConsumerB->>DB: Notification 10 조회
    DB-->>ConsumerB: PENDING

    ConsumerA->>Redis: dispatch-lock:10 획득
    Redis-->>ConsumerA: 성공
    ConsumerB->>Redis: dispatch-lock:10 획득
    Redis-->>ConsumerB: 실패

    ConsumerA->>Sender: 외부 발송
    Sender-->>ConsumerA: 성공
    ConsumerA->>DB: SENT 저장
    ConsumerB-->>Kafka: 발송 건너뜀
```

현재 구현은 완료 상태 체크와 Redis 분산락 포트를 함께 사용한다.
기본 설정은 Redis 없이 동작하는 dummy 락이고, `notification.dispatch-lock.type=redis`로 Redis 락을 활성화한다.

Consumer가 락을 획득하고 `PROCESSING`으로 바꾼 뒤 종료되면 알림이 `PROCESSING` 상태로 남을 수 있다.
락은 TTL이 지나면 사라지지만, DB 상태는 자동으로 돌아가지 않는다.
따라서 운영 단계에서는 `PROCESSING` 상태가 일정 시간 이상 지속된 알림을 어떻게 복구할지도 정해야 한다.
외부 발송 전에 죽은 경우는 재시도할 수 있지만, 외부 발송 성공 후 `SENT` 저장 전에 죽은 경우는 재시도가 실제 중복 발송이 될 수 있다.
이 때문에 실제 외부 API 연동 시에는 idempotency key 전달이 중요하다.

## Week2 재처리와 중복 처리

Week2에서는 실패한 알림을 바로 최종 실패로 끝내지 않고, 실패 종류에 따라 `RETRY_WAIT`, `FAILED`, `DEAD`로 나눈다.

재처리와 중복 가능성은 항상 함께 다룬다.
`RETRY_WAIT` 상태의 알림은 retry poller가 다시 Kafka WORK 메시지로 발행하므로, Kafka에는 같은 `notificationId`가 여러 번 들어갈 수 있다.
이는 설계상 허용한다.
대신 Consumer는 다음 순서로 중복 발송을 막는다.

```text
Notification 조회
 -> SENT/FAILED/DEAD면 skip
 -> Redis dispatch-lock:{notificationId} 획득
 -> PROCESSING 변경
 -> Mock Send API 호출
 -> 결과 상태 저장
 -> lock 해제
```

`RETRY_WAIT`는 최종 상태가 아니므로 재처리 대상이다.
`FAILED`는 재시도하지 않는 실패, `DEAD`는 자동 재시도 한도를 초과한 운영자 확인 대상이다.

Mock API 호출 성공 후 DB에 `SENT`를 저장하기 전에 Consumer가 죽는 경우는 DB 상태만으로 중복 발송을 완전히 막기 어렵다.
따라서 Mock API 요청에는 `requestId`를 포함하고, 실제 외부 API로 바꿀 때도 같은 값을 idempotency key로 전달하는 설계를 유지한다.

## 키 선택 기준

외부 발송 API가 멱등성 키를 지원한다면 `requestId`를 `Idempotency-Key` 후보로 사용한다.
`requestId`는 클라이언트의 같은 발송 의도를 나타내므로, 사용자가 기대하는 중복 방지 의미와 가장 가깝다.
`notificationId`는 서버 내부에서 생성된 row 식별자라서 Consumer 처리 대상과 Redis 락 키로는 적합하지만, 외부 API 관점의 "같은 요청"을 표현하는 키로는 `requestId`보다 의미가 약하다.
예를 들어 동시 중복 요청 복구가 깨져 같은 발송 의도로 알림 row가 두 개 생기는 장애가 발생하면 `notificationId`는 서로 달라져 외부 중복 방지에 실패한다.
반대로 같은 `requestId`를 외부 idempotency key로 쓰면 서버 내부 row가 달라져도 클라이언트가 의도한 같은 요청이라는 의미를 유지할 수 있다.

Kafka record key와 Redis 락 키는 `notificationId`를 사용한다.
이 단계에서는 이미 서버에 알림 row가 만들어진 뒤이므로, Consumer가 처리해야 하는 대상은 클라이언트 요청이 아니라 DB에 저장된 단건 알림이다.

`OutboxEvent.id`는 Outbox row를 추적하기 위한 내부 ID로만 사용한다.
같은 알림에 대해 Outbox 이벤트가 재생성되거나 이벤트 종류가 늘어날 수 있으므로, 외부 발송 중복 방지 키로 쓰기에는 의미가 맞지 않는다.

## 현재 구현 상태

- 구현됨: `requestId` unique 제약
- 구현됨: 동시 중복 등록 요청 시 unique 제약 위반 후 기존 알림 재조회
- 구현됨: Outbox 이벤트 저장과 Kafka 발행
- 구현됨: Outbox publisher의 DB 트랜잭션과 Kafka 발행 경계 분리
- 구현됨: Kafka record key로 `notificationId` 사용
- 구현됨: 이미 완료된 알림 상태면 Consumer 발송 흐름에서 건너뛰는 구조
- 구현됨: 외부 발송 직전 Redis 분산락
- 구현됨: Outbox `PROCESSING` 상태와 복구 poller
- 구현됨: 실제 Mock Send API HTTP 연동
- 구현됨: `RETRY_WAIT`, `DEAD` 상태 기반 재처리

## 정리

이 시스템의 중복 처리는 한 단계에서 모두 끝나는 문제가 아니다.
API 등록 단계는 `requestId`, 메시지 처리 단계는 `notificationId`, Outbox 추적은 `OutboxEvent.id`가 담당한다.
Kafka와 Outbox는 중복 발행 가능성을 열어두고, Consumer와 외부 발송 경계에서 멱등성과 락으로 실제 중복 발송을 막는 방향으로 설계한다.
