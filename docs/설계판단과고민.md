# 설계 판단과 고민

## 1. 단순 Async 대신 Kafka를 사용한 이유

처음에는 API 요청을 받은 뒤 내부 thread pool에 발송 작업을 넘기는 방식도 생각할 수 있다.
하지만 이 방식은 서버가 재시작되거나 죽으면 메모리에 있던 작업이 사라진다.

알림 발송은 요청 이력과 처리 상태를 추적할 수 있어야 한다.
그래서 작업을 메모리에만 두지 않고 DB와 Kafka에 남기는 방향을 선택했다.

Kafka는 메시지를 디스크 기반 로그로 저장하고 Consumer가 나중에 이어서 처리할 수 있다.
또 Consumer 수를 늘려 발송 처리량을 확장하기 쉽다.

## 2. Outbox를 추가한 이유

DB 저장 후 Kafka를 바로 호출하면 다음 문제가 생긴다.

```text
DB 저장 성공
Kafka 발행 실패
```

이 경우 알림 요청은 DB에 남았지만 Kafka에는 발송 작업이 없을 수 있다.
운영 관점에서는 이 불일치를 명확히 다뤄야 한다.

그래서 `Notification`과 `OutboxEvent`를 같은 DB 트랜잭션에 저장한다.
API 응답 조건도 Kafka 발행 완료가 아니라 `DB 저장 + Outbox 저장`으로 잡았다.

## 3. 즉시 발행과 polling을 함께 둔 이유

Outbox를 polling만으로 처리하면 구현은 단순하다.
하지만 매 주기마다 DB를 조회하고, 발행 지연도 polling interval에 묶인다.

현재 구현은 commit 이후 즉시 발행을 한 번 시도한다.
평상시에는 Kafka 발행 지연을 줄이고, 실패하면 Outbox 이벤트를 다시 `PENDING`으로 되돌려 polling이 재처리한다.

```text
commit 성공
 -> 즉시 발행 시도
 -> PROCESSING 변경
 -> 실패 시 PENDING 복귀
 -> polling 재처리
```

이 방식은 구현 복잡도를 크게 늘리지 않으면서, polling만 사용하는 방식보다 지연을 줄일 수 있다.

## 4. Outbox 조회 성능

Outbox는 계속 쌓일 수 있다.
단순히 `status = PENDING`만 조회하면 데이터가 많아질수록 느려질 수 있다.

그래서 polling 조회는 다음 형태로 제한했다.

```text
where status = PENDING
order by id asc
limit batchSize
```

이를 위해 `status, id` 복합 인덱스를 둔다.
commit 이후 즉시 발행은 특정 애그리거트 타입과 알림 ID의 `PENDING` Outbox 이벤트를 찾으므로 `aggregateType, aggregateId, status` 복합 인덱스도 둔다.

아직 남은 고민은 있다.

- 발행 완료된 Outbox를 계속 `PUBLISHED`로 보관할지
- 일정 기간 후 삭제 또는 archive할지
- publisher가 여러 대 뜰 때 같은 row를 중복 처리하지 않도록 조건부 update나 `SKIP LOCKED`를 둘지

## 5. requestId와 notificationId의 역할

`requestId`는 클라이언트 retry를 식별하기 위한 값이다.
같은 요청을 다시 보낸 경우 새 알림을 만들지 않기 위해 사용한다.

`notificationId`는 서버가 만든 알림 식별자다.
Kafka 메시지 key와 Consumer 처리 대상 식별자로 사용한다.

두 값의 역할은 다르다.

| 값 | 사용 위치 | 목적 |
| --- | --- | --- |
| `requestId` | API 등록 | 같은 클라이언트 요청 중복 방지 |
| `notificationId` | Kafka / Consumer | 저장된 알림 처리 대상 식별 |

## 6. Kafka record key

현재 Kafka record key는 `notificationId`다.
Consumer가 처리할 대상이 DB에 저장된 단건 알림이기 때문이다.

검토한 후보는 다음과 같다.

| 후보 | 장점 | 한계 |
| --- | --- | --- |
| `notificationId` | 처리 대상과 일치하고 분산이 비교적 고르다. | 사용자 단위 순서는 보장하지 않는다. |
| user ID | 사용자별 순서 보장이 쉽다. | 특정 사용자 트래픽이 많으면 hot partition 가능성이 있다. |
| channel | 채널별 격리가 쉽다. | 채널 수가 적어 분산 효과가 낮다. |
| random/null | 분산이 쉽다. | 재처리 추적과 순서 보장이 약하다. |

이번 범위에서는 단건 알림 처리가 중심이라 `notificationId`를 선택했다.

## 7. 단건 알림부터 구현한 이유

그룹/대량 발송을 먼저 넣으면 설계 범위가 크게 늘어난다.

- 수신자 목록 관리
- 그룹 상태
- 전체 건수, 성공 건수, 실패 건수 집계
- Consumer 동시 처리 시 카운트 충돌 방지

이번 과제에서는 단건 알림 흐름을 끝까지 완성하는 데 집중했다.
대량 발송이 필요해지면 `NotificationGroup`을 별도 애그리거트로 추가하는 방향이 낫다고 판단했다.

## 8. 현재 남은 과제

- Redis 분산락으로 Consumer 동시 중복 발송 방지
- Outbox retry count와 실패 사유 저장
- 발행 완료 Outbox 정리 정책
- 여러 Outbox publisher 실행 시 row 선점 전략
- 실제 외부 API 연동 시 timeout, rate limit, retry 정책
- API 서버와 Worker 서버의 물리적 분리

## 9. Outbox 개선 우선순위

Outbox 개선은 모든 보강을 한 번에 넣기보다 장애 영향이 큰 지점부터 순서대로 진행한다.

### 1순위: DB 트랜잭션과 Kafka 발행 분리

초기 Outbox publisher는 DB 트랜잭션 안에서 Kafka 발행 ack를 기다렸다.
Kafka 발행은 DB rollback으로 되돌릴 수 없는 외부 시스템 효과이므로, DB 트랜잭션 안에 넣어도 원자성이 생기지 않는다.
오히려 Kafka 지연 동안 DB 커넥션과 트랜잭션 자원을 오래 점유한다.

따라서 조회와 상태 변경만 짧은 DB 트랜잭션으로 처리하고, Kafka 발행은 트랜잭션 밖에서 수행하도록 분리했다.
이 변경은 Kafka 중복 발행 가능성을 없애는 작업이 아니다.
Outbox의 at-least-once 특성은 유지하고, 트랜잭션 경계를 실제 보장 범위에 맞추는 작업이다.

서비스 이름은 책임 기준을 따른다.
조회 전용은 `NotificationOutboxQueryService`, 상태 변경은 `NotificationOutboxModifyService`, 전체 발행 흐름 조립은 `NotificationOutboxPublishService`가 맡는다.
`TransactionService`처럼 구현 방식이 드러나는 이름은 피한다.

### 2순위: Kafka 발행 결과 확인

`kafkaTemplate.send()`는 비동기 발행이다.
결과를 기다리지 않고 성공 처리하면 브로커 수신 여부를 확인하지 않은 상태에서 Outbox를 완료 처리할 수 있다.

현재 구현은 `get(timeout)`으로 broker ack를 기다린 뒤 `PUBLISHED`로 변경한다.
`notification.kafka.publish-timeout-ms` 설정으로 Kafka 응답 지연 시 무기한 대기하지 않게 한다.
콜백 기반으로 바꿀 경우에도 성공 콜백 안에서 별도 DB 트랜잭션을 열어 `PUBLISHED`를 기록해야 한다.

API 응답은 계속 `202 Accepted`다.
이 응답은 실제 외부 발송 성공이 아니라 발송 요청이 DB와 Outbox에 접수되었다는 뜻이다.

### 3순위: Outbox 상태 선점

멀티 인스턴스 publisher에서는 여러 인스턴스가 같은 `PENDING` row를 동시에 읽을 수 있다.
이를 줄이려면 `PENDING -> PROCESSING -> PUBLISHED` 상태 흐름을 둔다.

현재 publisher는 발행 전에 row를 `PROCESSING`으로 바꾼다.
발행 성공 시 `PUBLISHED`로 바꾸고, 실패 시 retry 정책이 아직 없으므로 `PENDING`으로 되돌린다.

DB 기반 선점을 우선 검토한다.
조건부 update나 `select for update skip locked`가 후보이며, Redis publisher lock은 DB 선점이 맞지 않을 때 보조 수단으로 검토한다.

### 4순위: 실패 기록과 retry 정책

Outbox 발행 실패가 반복되면 운영자가 원인을 볼 수 있어야 한다.
`retryCount`, `lastFailureReason`, `lastFailedAt`을 추가하고, retry 초과 시 처리할 상태를 정한다.
발행 완료된 Outbox를 언제 삭제하거나 archive할지도 이 단계에서 함께 정리한다.

### 5순위: Consumer 중복 발송 방지

Kafka에는 같은 `notificationId` 메시지가 여러 번 들어갈 수 있다.
시간차가 있는 중복은 `SENT`, `FAILED`, `CANCELED` 같은 완료 상태 체크로 건너뛴다.
거의 동시에 처리되는 중복은 Redis `dispatch-lock:{notificationId}`로 막는다.

이 Redis 락은 Outbox publisher의 중복 발행을 막는 락이 아니다.
Kafka 중복 메시지가 실제 외부 발송 중복으로 이어지지 않게 하는 Consumer 경계의 락이다.
