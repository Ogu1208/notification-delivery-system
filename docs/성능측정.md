# 성능 측정

알림 발송 시스템의 성능 특성을 관측 스택 위에서 측정하고, 발견된 병목을 개선한 뒤 재측정하는 실험 기록.

**측정 목적** (수치 하나가 아니라 병목 위치를 찾고 해석하는 것이 목적):
1. 병목 위치 파악 — API / Kafka / Consumer / Mock API / DB / Redis / JVM 중 어디가 먼저 무너지는가
2. TPS 한계 관찰 — 안정 구간 처리량과 붕괴 지점
3. 운영 관점 지표 대시보드 정립 — 실제 서비스에서 무엇을 봐야 하는지

## 2. 핵심 개념 정리

각 지표를 해석하려면 배경 개념 이해가 선행 필요.

### 2.1 JIT 워밍업

JVM은 시작 시 자바 코드를 인터프리터로 실행 → 자주 호출되는 부분을 JIT 컴파일러가 네이티브 코드로 컴파일. 이 과정을 워밍업이라 하고, 첫 수십초는 실제 성능보다 느림. **측정 대상 구간은 워밍업 이후로 잡아야 함**.

콜드 스타트 요인: JIT 외에도 Hikari pool growth, Kafka Producer metadata fetch, Postgres query planner cache, OS page cache 등.

### 2.2 Kafka Consumer lag

Kafka 브로커에는 각 토픽 파티션마다 최신 offset(가장 최근 저장된 메시지 번호)이 있고, Consumer group마다 자기가 어디까지 소비했는지 offset을 기록. **lag = 최신 offset - consumer가 소비한 offset**.

- **lag = 0**: 생산과 소비가 동기화됨 (좋음)
- **lag 계속 증가**: consumer가 생산 속도 못 따라감 → 병목 (워커 부족)
- **lag이 튀었다가 회복**: 순간적 부하 후 정상화 (탄력적)

**partition별 lag skew**: 특정 partition에만 몰리면 key 분포 편향 (hot partition).

### 2.3 Kafka partition

Kafka 토픽은 여러 partition으로 나뉘어 저장됨. **partition 개수가 병렬 처리의 상한**.

- Consumer 스레드는 **partition 하나에 스레드 하나** 배정 (하나의 partition을 동시에 여러 스레드가 읽지 않음, 순서 보장 위해)
- partition 3개면 consumer 스레드 3개까지 유효
- consumer 스레드가 partition 수보다 많으면 나머지는 idle

즉 **partition 수 = 최대 병렬 처리 워커 수**.

### 2.4 Rate 기반 부하 vs VU 기반 부하

k6는 두 가지 부하 제어 방식:

**VU 기반** (`constant-vus`, 기본): 가상 사용자 N명이 각자 요청 → 완료 → 다음 요청 반복
- 앱 응답이 느려지면 VU들이 대기 → 실제 부하 자동 감소
- **함정**: 시스템 상한을 못 봄 (앱 성능에 부하가 맞춰 조정됨)

**Rate 기반** (`constant-arrival-rate`, `ramping-arrival-rate`): 초당 N개 요청을 강제로 던짐
- 앱이 느려져도 계속 던짐 → 요청이 큐잉되거나 실패 → **진짜 병목 노출**
- 성능 측정 정석

우리 시나리오 (load/stress/spike) 는 전부 rate 기반.

### 2.5 워밍업/Steady/Rampdown 3구간

부하 곡선을 세 구간으로 나눔:

```text
TPS
100 |         ______________________
    |        /                      \
    |       /                        \
    |      /                          \
  0 |_____/                            \____
    0    1m         6m                 6m30s
     [warmup ]  [    steady    ]  [ rampdown ]
```

- **워밍업**: 0 → 목표 rate 서서히 증가 (JIT/pool warmup 흡수)
- **Steady**: 목표 rate 유지, **측정 대상**
- **Rampdown**: 목표 rate → 0으로 감소 (in-flight 요청 완료, 급격한 종료 방지)

각 요청에 `phase: warmup|steady|rampdown` 태그 붙여서 통계 계산 시 steady만 필터링.

### 2.6 Hikari Connection Pool

앱과 DB 사이의 커넥션을 pool로 관리. 3가지 상태:

| 상태 | 의미 | 정상 |
|---|---|---|
| active | 지금 트랜잭션에 실제 사용 중 | 워크로드 비례 |
| idle | pool 대기 (즉시 재사용 가능) | `minimum-idle` 근처 |
| pending | **커넥션 못 얻어 대기 중인 스레드** | **항상 0** |

`pending > 0` 지속 = pool 부족 신호. 요청 지연의 흔한 원인.

### 2.7 GC pause

JVM이 heap 정리 시 애플리케이션 스레드를 잠깐 정지시킴 ("stop-the-world"). 응답 시간 튐의 주요 원인.

- **pause sum/s**: 초당 GC 정지 시간 합 (예: 0.01 = 1%)
- **pause max**: 최근 관측된 단일 GC pause 최대 시간

정상: minor GC ~1ms, sum/s < 0.005. 이상: major GC 자주 발생 + sum/s > 0.05.

### 2.8 JVM Thread 상태 6종

- **runnable**: 실행 중 or CPU 대기 (일하는 스레드)
- **timed-waiting**: 시간 제한 대기 (`sleep(N)`, `wait(N)`)
- **waiting**: 무기한 대기 (`wait()`, `join()`, `park()`)
- **blocked**: **synchronized 락 획득 대기 (lock contention)** ← 문제 신호
- **new**: 생성됐지만 아직 start() 안 됨
- **terminated**: 실행 완료

정상: runnable ~CPU 코어 수, waiting/timed-waiting 대부분(수백), blocked ≈ 0.

### 2.9 Cascading Failure

한 계층 병목이 옆 계층으로 전파되어 시스템 전체 붕괴로 이어지는 현상. 우리 실측에서 관찰됨 (섹션 4.3).

### 2.10 Prometheus scrape & staleness

Prometheus는 정해진 간격으로(우리는 5초) 각 target의 `/actuator/prometheus` 등을 HTTP GET으로 스크레이핑. 응답 못 받으면 그 구간 데이터 없음.

- Target이 다운되어 응답 못 하면 → 이후 5분간 값 없다가 stale로 마킹
- 대시보드 그래프에서 이 구간이 gap으로 보임
- **API가 붕괴해서 actuator 엔드포인트도 응답 못 주면 관측 자체가 붕괴** ← 실제 관찰됨

## 3. 측정 방법론

### 3.1 시나리오 개요

| 시나리오 | 부하 모양 | 시간 | 목적 |
|---|---|---|---|
| smoke | VU 1, 순차 요청 30초 | 30초 | 스크립트/환경 정상성 |
| load | 워밍업 1분 → 100 TPS 유지 5분 → 램프다운 30초 | 6분 30초 | 평상시 부하 baseline |
| stress | 계단식 램프 100→300→600→1000→1500 TPS, 각 계단 hold 2분 | 약 12분 | 붕괴 지점 발견 |
| spike | baseline 100 TPS → 순간 800 TPS 스파이크 → 복귀 | 약 6분 | 회복력 관찰 |
| (Phase 2) soak | 80 TPS 1시간 유지 | 약 1시간 | 장기 누적 문제 관찰 |

### 3.2 Mock 모드 조합

sendmock은 실제 외부 발송 API를 흉내내는 별도 프로세스. 두 모드로 대비 측정:

| 모드 | 설정 | 목적 |
|---|---|---|
| ALWAYS_SUCCESS | 100% 즉시 성공 | 순수 파이프라인 처리량 상한 |
| RANDOM | 25% 확률 800~4000ms 지연 + 10% 확률 500/503/429 실패 | 재시도 부담 포함 실제 부하 |

두 모드의 결과 대비가 **재시도 부담이 시스템에 얼마나 부담을 주는가**를 정량화.

### 3.3 관측 지표 (5개 대시보드)

| 대시보드 | 관점 |
|---|---|
| Application | JVM (heap, GC, threads), HTTP (TPS, latency), Hikari |
| Kafka | Consumer lag, producer/consumer latency, partition 편차 |
| Postgres | Connection, TPS, slow query, cache hit ratio |
| Redis | ops/s, latency, memory |
| Domain | **커스텀 지표** — 상태 전이(SENT/RETRY_WAIT/DEAD), dispatch lock, Outbox latency, Mock API 응답 |

Domain 대시보드가 비즈니스 관점의 핵심.

### 3.4 실행 절차


### 3.5 반복 정책

- 각 조합(시나리오 × 모드) 최소 2회 실행
- 1회차는 워밍업 영향 있어 대푯값 제외
- 2회차 이후 값 사용. 편차 15% 이상이면 3회차 추가 후 중앙값

| 최대 VU 사용 | 3 | 300 (max 상한 도달) | — |

**서버 지표 (steady 중간 시점)**:

| 계층 | 지표 | 값 | 해석 |
|---|---|---|---|
| Kafka lag | 5,518 | 워커가 심하게 못 따라감 |
| Worker CPU | 32.6% | CPU 여유 (병목 아님) |
| Worker Hikari active | 1 | DB 커넥션 병목 아님 |
| Domain SENT (5분간) | 378 | 예상 30,000 대비 1.3% |
| Domain RETRY_WAIT (5분간) | 46 | 재시도로 들어감 |
| Mock API 실패율 | 21.4% | RANDOM 설정 10% + timeout(3s 초과 지연) 추가 |
| 처리량 | 초당 1.4건 | 워커가 mock 대기하며 스레드 잡힘 |

**근본 원인 분석**:

**1. 진짜 병목 — Kafka topic partition = 1개**

```
Topic: single-notification-send  PartitionCount: 1
```

Kafka는 **partition 하나당 consumer 스레드 하나** 배정. partition 1개면 아무리 워커 인스턴스나 concurrency 늘려도 유효 스레드 1개만 활성.

**2. Consumer concurrency 설정 없음**

`@KafkaListener(topics = "...")` 만 있고 `concurrency` 옵션 없음 → Spring Kafka 기본 1.

**3. 워커의 순차 처리 구조**

단일 consumer 스레드가:
- Mock API 호출 (평균 ms ~ 최대 3s timeout)
- 응답 대기 (blocking)
- 상태 저장 (DB)
- 다음 메시지 poll

RANDOM 25% 지연이 800~4000ms 걸리므로 워커 처리량 급락. **초당 1.4건 처리** 관측.

**4. Cascading Failure — API까지 무너짐**

100 TPS가 계속 들어오는데 워커는 초당 1.4건 소화 → Kafka lag 5,000+ 폭증. 이게 API까지 다음 경로로 전파:

```
1. Worker 처리 지연 → Kafka lag 폭증
   ↓
2. app-api의 Outbox immediate publish 
   (@TransactionalEventListener(AFTER_COMMIT))가
   Kafka producer 호출 시 producer buffer(기본 32MB) 만원 상태
   ↓
3. producer.send() blocking → API 요청 스레드 대기
   ↓
4. Tomcat request thread pool (기본 200) 다 소진
   ↓
5. 새 HTTP 요청 큐잉 → 60초 timeout
   ↓
6. /actuator/prometheus 도 같은 Tomcat pool 사용 → 응답 못 함
   ↓
7. Prometheus scrape timeout → app-api 지표 전부 gap
```

**5. 관측 자체의 붕괴**

Prometheus targets 조회 결과, **app-api 컨테이너가 부하 시작 30초 만에 스크레이핑 실패로 DOWN**. 부하 종료 후에야 복귀. 그래서 붕괴 순간의 app-api 지표를 대시보드에서 볼 수 없었음 (그래프 gap으로만 확인).

이는 실전에서도 발생 가능한 문제:
- 시스템이 마비되면 관측 자체가 마비될 수 있음
- Actuator를 별도 스레드풀로 분리하거나
- Distributed tracing/log-based observation을 병행해야 안전

## 5. 발견된 병목과 개선 방향

### 5.1 즉시 개선 (1순위)

**A. Kafka topic partition 증가**
- 현재: 1개 → 개선: 6개
- 효과: 병렬 처리 최대 6배
- 방법: `kafka-topics --alter --partitions 6` (기존 topic)

**B. Consumer concurrency 설정**
- 현재: 기본 1 → 개선: 3~6
- 방법: `application.yml`의 `spring.kafka.listener.concurrency` 설정 또는 `@KafkaListener(concurrency = "3")`
- partition 수와 균형 필요 (concurrency > partition 시 유효 threads 제한됨)

### 5.2 구조적 개선 (2순위)

**C. Mock API 호출을 non-blocking으로 (WebClient/Reactive)**
- 현재 RestClient 동기 호출 → 워커 스레드가 응답 대기 시간 동안 잡힘
- Reactive 스타일로 바꾸면 소수 스레드로 다수 요청 처리 가능
- 다만 코드 변경 크므로 후순위

**D. Outbox immediate publish를 API 스레드에서 분리**
- 현재 `@TransactionalEventListener(AFTER_COMMIT)`가 API 스레드에서 동기 실행
- 별도 Executor로 이양 → API 응답이 Kafka 발행 상태와 독립
- Cascading failure 방지에 결정적

**E. Actuator 엔드포인트를 별도 포트/스레드풀로 분리**
- `management.server.port` 를 다르게 두면 관측 계층이 앱 마비에 안 휘말림
- 실전 운영에서 매우 중요

### 5.3 튜닝 (3순위)

**F. Mock read timeout 축소 (3s → 1.5s)**
- 4000ms 지연 요청을 timeout으로 fail fast → retry poller에 위임
- 워커 스레드 회수 속도 증가

**G. Kafka producer buffer.memory 증가**
- 32MB → 64MB or 128MB
- Cascading failure 지연 효과 (근본 해결은 아님, 병목 정리가 먼저)
