## 2. 핵심 개념 정리

각 지표를 해석하려면 배경 개념 이해가 선행 필요.

### 2.1 JIT 워밍업

JVM은 시작 시 자바 코드를 인터프리터로 실행 → 자주 호출되는 부분을 JIT 컴파일러가 네이티브 코드로 컴파일. 이 과정을 워밍업이라 하고, 첫 수십초는 실제 성능보다 느림. **측정 대상 구간은 워밍업 이후로 잡아야 함**.

콜드 스타트 요인: JIT 외에도 Hikari pool growth, Kafka Producer metadata fetch, Postgres query planner cache, OS page cache 등.

### 2.2 Kafka Consumer lag

Kafka 브로커에는 각 토픽 파티션마다 최신 offset(가장 최근 저장된 메시지 번호)이 있고, Consumer group마다 자기가 어디까지 소비했는지 offset을 기록. **lag = 최신 offset - consumer가 소비한 offset**.

- **lag = 0**: 생산과 소비가 동기화됨 (좋음)
- **lag 계속 증가**: consumer가 생산 속도 못 따라감 → 병목 (워커 부족)
- **lag이 튀었다가 회복**: 순간적 부하 후 정상화 (탄력적)

**partition별 lag skew**: 특정 partition에만 몰리면 key 분포 편향 (hot partition).

### 2.3 Kafka partition

Kafka 토픽은 여러 partition으로 나뉘어 저장됨. **partition 개수가 병렬 처리의 상한**.

- Consumer 스레드는 **partition 하나에 스레드 하나** 배정 (하나의 partition을 동시에 여러 스레드가 읽지 않음, 순서 보장 위해)
- partition 3개면 consumer 스레드 3개까지 유효
- consumer 스레드가 partition 수보다 많으면 나머지는 idle

즉 **partition 수 = 최대 병렬 처리 워커 수**.

### 2.4 Rate 기반 부하 vs VU 기반 부하

k6는 두 가지 부하 제어 방식:

**VU 기반** (`constant-vus`, 기본): 가상 사용자 N명이 각자 요청 → 완료 → 다음 요청 반복
- 앱 응답이 느려지면 VU들이 대기 → 실제 부하 자동 감소
- **함정**: 시스템 상한을 못 봄 (앱 성능에 부하가 맞춰 조정됨)

**Rate 기반** (`constant-arrival-rate`, `ramping-arrival-rate`): 초당 N개 요청을 강제로 던짐
- 앱이 느려져도 계속 던짐 → 요청이 큐잉되거나 실패 → **진짜 병목 노출**
- 성능 측정 정석

우리 시나리오 (load/stress/spike) 는 전부 rate 기반.

### 2.5 워밍업/Steady/Rampdown 3구간

부하 곡선을 세 구간으로 나눔:

```text
TPS
100 |         ______________________
    |        /                      \
    |       /                        \
    |      /                          \
  0 |_____/                            \____
    0    1m         6m                 6m30s
     [warmup ]  [    steady    ]  [ rampdown ]
```

- **워밍업**: 0 → 목표 rate 서서히 증가 (JIT/pool warmup 흡수)
- **Steady**: 목표 rate 유지, **측정 대상**
- **Rampdown**: 목표 rate → 0으로 감소 (in-flight 요청 완료, 급격한 종료 방지)

각 요청에 `phase: warmup|steady|rampdown` 태그 붙여서 통계 계산 시 steady만 필터링.

### 2.6 Hikari Connection Pool

앱과 DB 사이의 커넥션을 pool로 관리. 3가지 상태:

| 상태 | 의미 | 정상 |
|---|---|---|
| active | 지금 트랜잭션에 실제 사용 중 | 워크로드 비례 |
| idle | pool 대기 (즉시 재사용 가능) | `minimum-idle` 근처 |
| pending | **커넥션 못 얻어 대기 중인 스레드** | **항상 0** |

`pending > 0` 지속 = pool 부족 신호. 요청 지연의 흔한 원인.

### 2.7 GC pause

JVM이 heap 정리 시 애플리케이션 스레드를 잠깐 정지시킴 ("stop-the-world"). 응답 시간 튐의 주요 원인.

- **pause sum/s**: 초당 GC 정지 시간 합 (예: 0.01 = 1%)
- **pause max**: 최근 관측된 단일 GC pause 최대 시간

정상: minor GC ~1ms, sum/s < 0.005. 이상: major GC 자주 발생 + sum/s > 0.05.

### 2.8 JVM Thread 상태 6종

- **runnable**: 실행 중 or CPU 대기 (일하는 스레드)
- **timed-waiting**: 시간 제한 대기 (`sleep(N)`, `wait(N)`)
- **waiting**: 무기한 대기 (`wait()`, `join()`, `park()`)
- **blocked**: **synchronized 락 획득 대기 (lock contention)** ← 문제 신호
- **new**: 생성됐지만 아직 start() 안 됨
- **terminated**: 실행 완료

정상: runnable ~CPU 코어 수, waiting/timed-waiting 대부분(수백), blocked ≈ 0.

### 2.9 Cascading Failure

한 계층 병목이 옆 계층으로 전파되어 시스템 전체 붕괴로 이어지는 현상.

전형적 패턴 (우리 실측에서 관찰됨, [실험-01](실험-01-baseline.md#43-load-random-100-tps--붕괴-발견) 참고):
1. Worker 처리 지연 → Kafka lag 폭증
2. Producer buffer 만원 → API의 producer.send() blocking
3. API Tomcat thread pool 소진 → 새 요청 큐잉/timeout
4. `/actuator/prometheus` 도 같은 pool → 관측 자체 마비

### 2.10 Prometheus scrape & staleness

Prometheus는 정해진 간격으로(우리는 5초) 각 target의 `/actuator/prometheus` 등을 HTTP GET으로 스크레이핑. 응답 못 받으면 그 구간 데이터 없음.

- Target이 다운되어 응답 못 하면 → 이후 5분간 값 없다가 stale로 마킹
- 대시보드 그래프에서 이 구간이 gap으로 보임
- **API가 붕괴해서 actuator 엔드포인트도 응답 못 주면 관측 자체가 붕괴** ← 실측됨

## 3. 시나리오 정의

| 시나리오 | 부하 모양 | 시간 | 목적 |
|---|---|---|---|
| smoke | VU 1, 순차 요청 30초 | 30초 | 스크립트/환경 정상성 |
| load | 워밍업 1분 → 100 TPS 유지 5분 → 램프다운 30초 | 6분 30초 | 평상시 부하 baseline |
| stress | 계단식 램프 100→300→600→1000→1500 TPS, 각 계단 hold 2분 | 약 12분 | 붕괴 지점 발견 |
| spike | baseline 100 TPS → 순간 800 TPS 스파이크 → 복귀 | 약 6분 | 회복력 관찰 |
| (Phase 2) soak | 80 TPS 1시간 유지 | 약 1시간 | 장기 누적 문제 관찰 |

### Mock 모드 조합

sendmock은 실제 외부 발송 API를 흉내내는 별도 프로세스. 두 모드로 대비 측정:

| 모드 | 설정 | 목적 |
|---|---|---|
| ALWAYS_SUCCESS | 100% 즉시 성공 | 순수 파이프라인 처리량 상한 |
| RANDOM | 25% 확률 800~4000ms 지연 + 10% 확률 500/503/429 실패 | 재시도 부담 포함 실제 부하 |

두 모드의 결과 대비가 **재시도 부담이 시스템에 얼마나 부담을 주는가**를 정량화.

## 7. 완전 리셋 절차 (실험 반복 사이)

시스템 상태를 완전히 초기화하고 다음 실험 시작하려면:

```bash
# 1. 앱 컨테이너 중지 (Kafka 백로그 소화 중단)
docker compose -f compose.yaml -f docker-compose.observability.yml stop app-api app-worker

# 2. Kafka topic 삭제 (백로그 제거)
docker compose exec -T kafka kafka-topics --bootstrap-server localhost:9092 --delete --topic single-notification-send

# 3. Kafka topic 재생성 (원하는 partition 수로)
docker compose exec -T kafka kafka-topics --bootstrap-server localhost:9092 --create \
  --topic single-notification-send --partitions <N> --replication-factor 1

# 4. DB truncate
docker compose exec -T postgres psql -U notification -d notification < scripts/perf/reset.sql

# 5. 앱 재기동 (설정 변경했으면 --build)
docker compose -f compose.yaml -f docker-compose.observability.yml up -d [--build] app-api app-worker

# 6. verify
sleep 30
./scripts/perf/verify-setup.sh
```
