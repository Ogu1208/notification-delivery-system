# 실험 06 — HC5 bean 격리 해제 재부하

실험-05로 근본 병목(sync outbox listener + Hikari 소진 경로)이 제거된 상태에서 실험-03의 격리 C를 해제하면 정말 HC5 bean이 app-api에 있어도 안정한지 검증. 안정하면 실험-03의 mechanism 미스터리는 자연 해소 — HC5 자체는 문제가 아니고, cascade 방아쇠였을 뿐이라는 해석 확정.

배경 개념과 실행 절차는 [방법론.md](방법론.md) 참고. 관련 실험은 [실험-03-httpclient5.md](실험-03-httpclient5.md), [실험-05-outbox-async.md](실험-05-outbox-async.md) 참고.

---

## 1. 배경과 가설

### 1.1 두 개의 확정된 empirical fact

- 실험-03: HC5 bean이 app-api에 존재하면 sync outbox listener 상태에서 반복 붕괴. Bean 격리로 안정 회복. Mechanism 미확정
- 실험-05: Sync outbox listener를 `@Async`로 분리하면 근본 병목 제거. Hikari 소진 경로 자체 차단

### 1.2 가설

실험-03의 붕괴는 다음 두 조건의 조합이었을 가능성:
- HC5 bean이 app-api에 존재해 소소한 부하 유발
- Sync outbox listener가 이 소소한 부하를 tip over 방아쇠로 만들어 Hikari 소진 유발

이 가설이 맞다면, **실험-05로 sync 병목이 사라진 상태에서는 HC5 bean이 app-api에 있어도 안정해야 함**. 방아쇠는 있어도 폭발할 도미노가 없기 때문.

가설이 틀리면 (여전히 붕괴하면) HC5 자체가 sync 병목과 무관한 별도 mechanism으로 시스템을 무너뜨린다는 뜻 → 추가 조사 필요.

## 2. 적용 내용

`MockSendApiClient`의 `@ConditionalOnProperty` 제거. 나머지 5개 bean(senders/router/dispatch)은 그대로 유지해 app-api가 mock을 실제 호출하는 상태로는 만들지 않음.

```java
// 이전 (격리)
@Component
@ConditionalOnProperty(name = "notification.role.worker-enabled", havingValue = "true")
public class MockSendApiClient { ... }

// 이번 (격리 해제)
@Component
public class MockSendApiClient { ... }
```

app-api 상태:
- HC5 bean(`MockSendApiClient`) **등록됨** — IdleConnectionEvictor 스레드, class loading, metaspace 사용
- Senders/router 없음 → HC5는 등록만 되어있고 실제 호출은 없음
- Outbox listener는 `@Async` (실험-05 상태 유지)

이는 실험-03의 격리 C 이전 상태(bean 존재만 함)와 동일한 조건이되, **outbox만 async로 바뀐 차이**.

## 4. 해석

### 4.1 가설 완전 확정

HC5 bean이 app-api에 존재해도 완전 안정. Hikari pending 계속 0, active max 5로 실험-05보다 오히려 낮음. 응답시간 지표도 실험-05와 동등 이상. **실험-03의 "HC5 bean 존재 자체가 app-api를 무너뜨렸다"는 empirical fact는 sync outbox listener 상태에서만 성립하는 조건부 사실이었음**.

### 4.2 실험-03 mechanism 미스터리 자연 해소

실험-03 이후 미확정으로 남겨두었던 "HC5 bean이 어떤 mechanism으로 app-api를 무너뜨리는가"의 답:
- **HC5 자체가 시스템을 무너뜨린 것이 아님**
- HC5는 소소한 부하(evictor 스레드, class loading 등)를 유발했을 뿐
- 이 소소한 부하가 **sync outbox listener라는 취약점을 만나면 cascade의 방아쇠**로 작동한 것
- 근본 병목(Hikari 소진 경로)이 제거된 상태에서는 방아쇠가 있어도 폭발할 도미노가 없음

즉 실험-03의 붕괴는 "HC5 + sync outbox listener" **두 조건의 조합**에서만 발생. 실험-05가 sync 조건을 제거하니 자연스럽게 HC5 조건 단독으론 무해해짐.

### 4.3 실험-05의 p99 44 ms는 노이즈였을 가능성

실험-05 p99: 44.6 ms
실험-06 p99: 31.48 ms

두 실험은 outbox `@Async` 상태 동일하고 HC5 bean 위치만 다름. HC5 격리 해제로 p99가 좋아질 이유는 없으므로, **실험-05의 44 ms는 1회 실행 노이즈였을 가능성이 높음**. 실은 실험-03의 격리 A/C p99(33.6 / 37.2 ms) 범위로 자연 회귀. Kafka async batch나 ZGC 튜닝 같은 개선 착수는 **더 신중하게 판단해야 함** — 애초에 재현되는 문제가 아닐 수 있음.

### 4.4 Bean 격리의 근거를 성능에서 아키텍처로 재정립

성능 관점에서는 이제 격리 불필요 (실험-06으로 증명). 그러나 격리 자체는 **다른 이유로 유지 결정**:

- **역할 분리 원칙**: Mock 발송은 worker 노드의 관심사. API 노드는 요청 접수와 Kafka publish만 담당. `@ConditionalOnProperty`는 이 역할 분리를 코드에 명시하는 수단
- **일관성**: senders/router/dispatch 5개 bean은 이미 격리 유지 중. MockSendApiClient만 해제하면 6개 중 1개만 다른 규칙이 됨
- **멀티모듈 전환 대비**: 향후 `app-api` / `app-worker` 모듈 분리 시 이 코드는 자연스럽게 `app-worker` 모듈로 이동 (어노테이션 → 모듈 이동으로 리팩토링)
- **실험 결과와 모순 아님**: "성능 관점에선 불필요, 아키텍처 관점에선 필요"의 다른 층위 판단

## 5. 다음 단계

### 5.1 즉시 조치

- **`MockSendApiClient.@ConditionalOnProperty` 복구 유지**. 성능 관점에선 불필요하지만 § 4.4의 아키텍처 근거로 유지 결정
- 코드 주석에 "성능 이유 아닌 역할 분리 원칙으로 유지" 명시 (향후 이 코드를 볼 때 실험-06 결과를 알고 있는 것처럼 오해받지 않도록)
- 다른 5개 bean(senders/router/dispatch)도 격리 유지 유지 — 일관성 유지

### 5.2 실험-03 문서 후속 정정

실험-03 문서에 "mechanism 미확정으로 남김" 부분을 실험-06 결과로 해소된 것으로 update 필요. 실험-06 링크와 결론 반영.

### 5.3 실험-05의 p99 개선 후보 재평가

p99 44 ms가 노이즈였을 가능성이 크므로, [실험-05 § 5.2](실험-05-outbox-async.md#52-p99-tail-latency-개선-후보-다음-작업)의 개선 후보(Kafka async batch, ZGC, prestart)는 **재현 확인 없이는 착수하지 않음**. 우선순위 낮춤.
