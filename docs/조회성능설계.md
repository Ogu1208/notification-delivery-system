# 조회 성능 설계

알림 발송 이력 조회를 별도 API로 추가한다고 가정할 때, 어떤 조회 패턴을 핵심으로 두고 어떤 인덱스·페이징·운영 전략을 붙여야 하는지 정리한 문서다.
이 프로젝트 요구사항(`docs/요구사항.md`)에는 조회 API가 포함되어 있지 않으므로, 이 문서는 "요구사항 이상 기능"을 도입할 때 판단 근거를 남기기 위한 설계 문서다.

기존 설계 판단 흐름은 `docs/설계판단과고민.md`를, 도메인 필드 정의는 `도메인모델.md`를 함께 참고한다.

## 1. "최근 7일"은 정말 가벼운 조회인가

겉으로는 최근 7일만 보면 되는 것 같지만, 그것만으로는 조회가 가벼워지지 않는다.

- 테이블 전체에는 7일보다 오래된 데이터가 계속 누적되어 있다. 조회 범위가 7일이라는 것과 저장 데이터가 7일이라는 것은 다르다.
- 인덱스가 조회 패턴에 맞지 않으면 "7일치만" 필터하기 위해 그보다 훨씬 많은 row를 훑어야 한다.
- 정렬 + 페이징이 붙으면 필터가 잘 되어도 뒤 페이지로 갈수록 비용이 커진다.

### 정렬 + 페이징의 함정

최근순 정렬을 해야 하는데 인덱스가 정렬 순서를 지원하지 않으면, 조건 필터링은 되더라도 결과를 정렬하는 비용이 남는다.
`OFFSET N` 방식이라면 뒤 페이지로 갈수록 앞의 N개를 훑고 버리는 비용이 붙는다.
데이터가 많을수록 이 비용은 조용히 커지며, 부하 테스트를 하기 전까지는 잘 드러나지 않는다.

## 2. 이 프로젝트에서 상정하는 조회 패턴

먼저 지금 우리 도메인에 어떤 컬럼이 있고, 조회에 무엇을 요구할 수 있는지 정리한다.

`Notification` (BaseEntity 포함) 주요 컬럼:

- `id`, `request_id` (UNIQUE), `receiver`, `channel`, `status`
- `sending_started_at`, `sent_at`, `failed_at`, `last_failed_at`, `next_retry_at`
- `created_at`, `updated_at`

핵심 조회 시나리오 후보:

- (A) 요청자별 최근 7일, 최신순 페이징 — 이번 설계 문서의 주 시나리오
- (B) 상태별 조회 (SENT / FAILED / RETRY_WAIT / DEAD)
- (C) 수신자별 최근 7일 조회

"요청자(`requester_id`)"의 의미는 이 시스템에서 **알림 발송을 API로 호출한 서비스/시스템 식별자**다 (예: `order-service`, `payment-service`). 개인 사용자(user)나 개별 요청 UUID(`request_id`)와 혼동하지 않는다.

- `request_id`: "이 요청 한 건"의 UUID. UNIQUE, retry 판별용.
- `requester_id`: "누가 이 요청을 보냈는가". 상위 호출 서비스. 조회 필터 기준 컬럼.
- `receiver`: "누구에게 보내는가". 이메일/전화번호 등 채널별 수신 대상.

Phase 0에서 `Notification`에 `requester_id` 컬럼을 도입했다. 조회는 이 값 또는 `receiver` 기준으로 이뤄진다.

## 3. 인덱스는 "컬럼을 추가"가 아니라 "조회 패턴 설계"다

인덱스를 붙일지 말지는 "이 컬럼이 자주 쓰이는가"가 아니라 "어떤 조회 패턴을 만족시켜야 하는가"로 결정한다.

세 가지를 항상 같이 본다.

- WHERE 조건에 무엇이 들어가는가
- ORDER BY 기준은 무엇인가
- 자주 같이 묶여 조회되는 컬럼은 무엇인가

### 예시 — 요청자별 최근 7일, 최신순

같은 조회를 두 인덱스로 지원한다고 가정한다.

- 단일 인덱스 `(requester_id)`
  - `requester_id`로 필터는 잘 된다.
  - 하지만 최근순 정렬을 위해 별도 Sort 단계가 남는다.
  - 결과 수가 많으면 정렬 비용이 그대로 남는다.
- 복합 인덱스 `(requester_id, created_at DESC)`
  - 필터와 정렬을 한 인덱스로 함께 흡수한다.
  - `WHERE requester_id = ? AND created_at >= now() - interval '7 day' ORDER BY created_at DESC LIMIT ?` 형태에 잘 맞는다.
  - 페이징 커서(§5)로도 자연스럽게 이어진다.

상태 필터가 자주 붙는다면 다음도 후보다.

- `(requester_id, status, created_at DESC)`
  - "상태 = SENT인 것만 최근순" 같은 조회에 맞는다.
  - 단, 상태 필터가 대부분의 조회에 붙는 게 아니라면 오히려 인덱스 유지 비용만 늘 수 있다.

컬럼 순서 원칙: **등호(=) 조건 → 범위/정렬 조건**.
`requester_id = ? AND created_at >= ? ORDER BY created_at DESC`에서 `requester_id`가 앞, `created_at`이 뒤인 이유는 이 원칙 때문이다.

### 인덱스 설계 기준 세 가지

인덱스 컬럼 순서는 감이 아니라 다음 기준을 순서대로 적용해 결정한다.

#### (1) 카디널리티가 높은 등호 조건 컬럼을 선두에

인덱스는 B-Tree 구조라 왼쪽(선두) 컬럼부터 정렬된다.
선두 컬럼에서 후보 데이터를 얼마나 좁힐 수 있는지가 전체 성능을 좌우한다.

- `requester_id`처럼 항상 `= ?` 형태로 오고 값의 종류가 많은 컬럼은 선두 후보다.
- `status`는 값이 6종뿐이라 카디널리티가 낮다. 선두로는 잘 안 맞고, 필터로 자주 붙는 경우 뒤 컬럼으로 둔다.
- 값 분포가 심하게 편향된 경우(예: 대부분 `SENT`)에는 카디널리티 수치보다 **실제 조회 값의 선택도**가 더 중요하다. Postgres 통계(`pg_statistic`)가 이걸 반영하는지 확인한다.

#### (2) 범위 조건은 등호 조건 뒤에

B-Tree 인덱스에서 범위 조건(`>=`, `<`, `BETWEEN`)이 등장하면, **그 이후 컬럼은 인덱스 스캔 범위를 좁히는 데 활용되지 않는다**. 필터로만 쓰인다.
Postgres EXPLAIN에서 이 차이는 `Index Cond`와 `Filter` 로 드러난다.

- `(requester_id =, created_at >=, status =)` 순서에서는 세 번째 `status`가 filter가 된다.
- 조회할 때마다 `status` 등호가 함께 온다면 순서를 바꿔 `(requester_id, status, created_at)`으로 두는 게 낫다.
- 정렬(`ORDER BY`)도 사실상 "범위 조건에 준하는" 위치라, 정렬 컬럼은 등호 컬럼들 뒤에 둔다.

#### (3) 정렬 방향을 인덱스에 반영

`ORDER BY created_at DESC LIMIT ?` 형태라면 인덱스도 `(..., created_at DESC)`로 정의하면 Sort 노드가 사라진다.
PostgreSQL과 MySQL 모두 ASC 인덱스를 backward scan해서 DESC 정렬을 처리할 수 있지만, 커서 페이징 조건과 방향을 정확히 맞추려면 인덱스 정의와 ORDER BY 방향을 일치시키는 게 실수를 줄인다.

### PostgreSQL과 MySQL 인덱스 설계 차이

위 (1)(2)(3)은 **B-Tree 자료구조 자체 성격이라 MySQL과 PostgreSQL 모두 동일하게 적용된다**. 이 프로젝트는 부하 테스트를 Postgres 기반으로 하니(`docs/성능측정/`), 엔진 차이가 나는 지점만 별도로 정리해 둔다.

#### Covering index / Index-Only Scan

- MySQL InnoDB: 테이블이 PK로 물리 정렬(clustered)되고, 모든 세컨더리 인덱스 리프에 PK가 자동 포함된다. 그래서 EXPLAIN `Extra`에 `Using index`가 자연스럽게 잡힌다.
- PostgreSQL: heap-organized. Index-Only Scan을 뽑으려면 두 조건이 모두 필요하다.
  1. 필요한 컬럼이 모두 인덱스에 있어야 한다. SELECT 절에만 있는 컬럼은 `INCLUDE`(PG 11+)로 넣을 수 있다.

     ```sql
     CREATE INDEX idx_notification_requester_created
       ON notification (requester_id, created_at DESC)
       INCLUDE (status, channel, receiver);
     ```

  2. 해당 페이지의 visibility map이 all-visible이어야 한다. 최근에 쓰기가 많이 있었다면 VACUUM 전까지 `Heap Fetches: N`이 남는다.
- EXPLAIN에서 `Index Only Scan` + `Heap Fetches: 0`이 함께 나오는지가 확인 포인트다.

#### Partial Index

- PostgreSQL: `CREATE INDEX ... WHERE status = 'PENDING'` 지원.
- MySQL 8: 미지원.
- Outbox의 `WHERE status = 'PENDING' ORDER BY id`처럼 특정 상태만 자주 조회되는 경우 partial index가 전체 인덱스보다 훨씬 작고 유리하다.

#### 여러 인덱스 조합 (Bitmap Index Scan)

- PostgreSQL은 여러 단일 컬럼 인덱스를 Bitmap Index Scan으로 결합할 수 있다.
- MySQL의 Index Merge는 존재하지만 실무적으로 자주 뽑히지 않는다.
- 결론: MySQL이라면 복합 인덱스로 확실히 커버해야 안전한 반면, PostgreSQL은 상황에 따라 단일 인덱스 조합으로도 통한다. 그래도 "핵심 조회는 복합 인덱스로 확실히 잡는다"는 원칙은 그대로 유지한다.

#### BRIN 인덱스 (PostgreSQL만)

- 데이터가 삽입 순서와 물리 저장 순서가 대체로 일치하는 시계열 성격이면 후보다.
- `created_at` 기준 최근 7일 조회는 대상 블록이 좁게 뭉쳐 있어 BRIN이 매우 작게 유지된다.
- 지금 규모에서는 B-Tree로 충분하다. 데이터가 매우 커진 뒤에도 B-Tree 유지 비용이 부담이면 검토 대상이다.

#### MVCC와 인덱스 bloat

- PostgreSQL의 업데이트는 dead tuple을 남기는 방식이라 인덱스에도 bloat가 쌓인다. autovacuum이 처리하지만, 대량 삽입/업데이트 뒤 실행 계획이 갑자기 나빠지면 `pg_stat_user_indexes`, `pg_stat_progress_vacuum`을 먼저 본다.
- MySQL InnoDB는 undo log 기반이라 bloat 관리 감각이 다르다.

### 이 프로젝트에서 이미 같은 판단을 한 사례

Outbox 인덱스는 다음 세 가지를 두고 있다 (`도메인모델.md` OutboxEvent 규칙 참고).

- `(status, id)` — polling 조회 (`WHERE status = PENDING ORDER BY id ASC LIMIT ?`)
- `(status, updated_at)` — 오래 PROCESSING인 이벤트 복구 조회
- `(aggregate_type, aggregate_id, status)` — 특정 알림의 발행 대기 이벤트 조회

세 인덱스 모두 "조회 패턴 → 컬럼 순서"의 결과다. 조회 API 인덱스도 같은 방식으로 결정하면 된다.

## 4. EXPLAIN을 남기는 습관

인덱스 결정은 논리적 근거만으로 끝나지 않는다. 실행 계획으로 확인해야 한다.

- 인덱스 추가 전/후 실행 계획을 각각 남긴다.
- H2는 `EXPLAIN`, Postgres는 `EXPLAIN (ANALYZE, BUFFERS)`를 쓴다.
- 확인 포인트:
  - Index Scan / Index Range Scan이 실제로 사용되는가
  - Sort 노드가 사라졌는가 (인덱스가 정렬까지 흡수했는가)
  - "examined rows / returned rows" 비율이 지나치게 크지 않은가
  - 페이징 뒷 페이지에서도 실행 시간이 안정적인가

문서화 관례는 `docs/성능측정/`의 실험 문서 형식(Before/After 지표를 붙이는 방식)을 그대로 따른다.
성능이 문제된 뒤가 아니라, 인덱스를 추가한 시점에 근거를 함께 남기는 게 목적이다.

### 실제 EXPLAIN 결과 (100만 row, Postgres 16)

시딩 조건: 20개 서비스 × 10만 명 사용자 × 3개 채널, `createdAt` 최근 30일 랜덤. 스크립트는 `scripts/perf/seed_notifications.sql`, `scripts/perf/explain_search_queries.sql`.

**재현 절차** (postgres 컨테이너만 있으면 됨):

```bash
# 1. Postgres 컨테이너 up
docker compose up -d postgres

# 2. 앱 스키마가 없으면 한 번 앱 잠깐 띄워 Hibernate가 스키마 생성하게 하고 stop
#    (기존 볼륨에 스키마 있으면 건너뜀)

# 3. 재시딩 (실험 직전마다 실행 — 시딩의 created_at 분포가 실행 시점 기준 상대 시간이라
#    시간이 흐르면 조회 조건이 잡는 범위가 좁아지기 때문)
docker compose exec -T postgres psql -U notification -d notification \
  -c "TRUNCATE notification RESTART IDENTITY CASCADE;"
docker compose exec -T postgres psql -U notification -d notification \
  < scripts/perf/seed_notifications.sql

# 4. EXPLAIN 시나리오 실행
docker compose exec -T postgres psql -U notification -d notification \
  < scripts/perf/explain_search_queries.sql

# 5. 필요하면 psql 직접 접속해 개별 시나리오 확인 / 인덱스 조작
docker compose exec postgres psql -U notification -d notification
```

각 시나리오를 15회 반복 실행 후 첫 5회(warmup) 버리고 남은 10회의 **median** 사용. 실제 서비스는 대개 warm 상태이므로 이 수치가 사용자 체감 latency에 가깝다.

| 시나리오 | 인덱스 사용 | Execution Time (warm median) | 비고 |
|---|---|---|---|
| A. 요청자 첫 페이지 | `idx_notification_requester_created` Backward Scan | **0.118 ms** | 인덱스 정렬 방향과 `ORDER BY DESC` 일치 → 실질 sort 없음 |
| B. 요청자 커서 있는 깊은 페이지 (튜플 비교 + 3컬럼 인덱스) | 같은 인덱스, 튜플 비교 전체가 Index Cond | **0.099 ms** | Filter/Sort 사라짐. 첫 페이지와 유사한 속도 |
| C. 수신자 첫 페이지 | `idx_notification_receiver_created` Backward Scan | **0.036 ms** | 카디널리티 높아서 매우 빠름 |
| D. 요청자 + 상태 필터 | 요청자 인덱스 + status Filter | **0.060 ms** | 요청자로 좁힌 뒤 status filter, 오버헤드 미미 |
| E. 요청자 + 채널 필터 | 요청자 인덱스 + channel Filter | **0.089 ms** | 요청자로 좁힌 뒤 channel filter |
| F. 요청자 + 수신자 조합 | 수신자 인덱스 + requester Filter | **0.037 ms** | Optimizer가 카디널리티 판단으로 좁은 쪽 인덱스 선택 |
| G. 단건 상세(`id = ?`) | PK Index Scan | **0.021 ms** | 예상대로 |

### 관측 1: 정렬 회피 확인

인덱스 정의 `(컬럼, created_at)`이 `ORDER BY created_at DESC, id DESC`와 방향 일치. `Index Scan Backward`로 sort 노드가 실질적으로 흡수됨. 계획에 `Incremental Sort`가 있어도 `Presorted Key: created_at`이라 실제 정렬은 발생하지 않는다. 인덱스 컬럼 순서 결정이 sort 회피에 유효했음을 검증.

### 관측 2: 커서 페이징 깊은 페이지의 100배 차이 (핵심 발견)

첫 페이지 0.38 ms vs 500번째 페이지 근처 38 ms. 원인 분석:

**첫 페이지 (A) 실행 과정** (warm ~0.12 ms)
- 조건: `requester_id = 'svc-5' AND created_at 범위`
- Optimizer가 이 조건 그대로 인덱스 range condition으로 매칭
- B-Tree에서 시작 지점 seek → `Index Scan Backward`로 뒤에서 앞으로 훑음
- 처음 21개 나오면 즉시 stop (`LIMIT 21`)
- 총 스캔 row 22개

**깊은 페이지 (B, JPQL OR 원본) 실행 과정** (warm median ~7.85 ms, cold ~40 ms)
- 조건에 커서 추가: `AND (created_at < X OR (created_at = X AND id < Y))`
- Postgres optimizer가 **OR 조건은 인덱스 range로 못 태움**
- 인덱스는 `requester_id + 7일 범위`까지만 태우고 스캔 (약 5000개)
- 그 중에서 커서 조건은 Row-by-Row Filter로 확인
- `Rows Removed by Filter: 4652` — 이만큼 훑고 버림
- 총 스캔 row 약 5000개, 첫 페이지(A) 대비 warm 기준 약 66배 느림

**왜 튜플 비교 syntax는 다른가**

Postgres는 row constructor comparison을 지원한다:

```sql
WHERE (created_at, id) < (:cursorCreatedAt, :cursorId)
```

이 syntax는 optimizer가 인덱스 range condition으로 정확히 매칭시킨다. B-Tree가 `(requester_id, created_at, id)` 순서면 이 조건 그대로 인덱스 위치를 계산해 커서 지점부터 seek → 21개만 스캔 → 종료. **첫 페이지와 유사한 속도가 나온다** (~1 ms 수준).

**JPQL의 한계**

JPQL은 표준 SQL의 일부만 지원하고, row constructor comparison `(a, b) < (x, y)`는 문법 자체를 지원하지 않는다. 현재 `NotificationSearchDao`가 JPQL로 다음과 같이 조립하는 이유가 이 때문:

```java
jpql.append(" and (n.createdAt < :cursorCreatedAt")
    .append(" or (n.createdAt = :cursorCreatedAt and n.id < :cursorId))");
```

이 OR 조건이 Postgres에서 인덱스에 못 태워지고 Filter로 처리된다.

**개선 방법**
- **native query 사용** (권장): `@Query(nativeQuery = true, value = "... WHERE (created_at, id) < (:cursorCreatedAt, :cursorId) ...")` — 튜플 비교 그대로. 코드 변경 규모 작음
- QueryDSL 도입: SQL-friendly한 표현식 조립. 다른 동적 쿼리에도 재사용
- JPQL 유지 + 재구조화: OR을 UNION 서브쿼리 두 개로 분리. 가능은 하지만 성능이 native 튜플 비교만큼 나오지 않고 복잡도만 늚

### 개선 적용 1단계: NotificationSearchDao를 native SQL + 튜플 비교로 교체

`NotificationSearchDao`가 JPQL을 native SQL로 재작성. 커서 조건을 `(created_at, id) < (:cursorCreatedAt, :cursorId)`로 변경.

같은 B 시나리오 (요청자 커서 있는 깊은 페이지) 재실행 (warm median):

| 상태 | Execution Time (warm median) | Filter로 제거된 row |
|---|---|---|
| 이전 (JPQL OR) | 7.85 ms | 4652 |
| **튜플 비교 native** | **0.20 ms** | 극소 (안 보임) |

**약 39배 개선** (~97% 감소). 그러나 실행 계획을 자세히 보면 튜플 비교의 첫 컬럼만 인덱스 range로 태워지고 `id`는 여전히 Filter로 처리된다:

```
Index Cond: (... AND created_at <= now() - 3 days ago)
Filter: ROW(created_at, id) < ROW(now() - '3 days'::interval, 500000)
```

**원인은 Postgres의 세컨더리 인덱스 구조**. Postgres 세컨더리 인덱스는 PK를 leaf에 자동 포함하지 않는다 (MySQL InnoDB의 Clustered Index Locator와 다름). `(requester_id, created_at)` 인덱스에 `id`가 없기 때문에 튜플 비교의 두 번째 컬럼(`id`)이 인덱스 range로 태워지지 않고 후처리된다.

### 개선 적용 2단계: 인덱스 key에 id 추가

`Notification` 엔티티의 `@Index columnList`를 `"requesterId, createdAt, id"`, `"receiver, createdAt, id"`로 확장. 앱을 통한 자동 반영은 컬럼 추가와 달리 index redefinition에는 잘 안 걸리므로, Postgres에서 수동으로 drop + create.

같은 B 시나리오 재실행 (warm median, 15회 중 5회 warmup 후 10회 median):

| 상태 | Execution Time (warm median) | Filter 여부 |
|---|---|---|
| 원본 (JPQL OR, 2컬럼 인덱스) | 7.85 ms | `Rows Removed by Filter: 4652` |
| 1단계 (튜플 비교, 2컬럼 인덱스) | 0.20 ms | id 부분만 Filter (극소) |
| **2단계 (튜플 비교, 3컬럼 인덱스)** | **0.10 ms** | **Filter 없음** |

**최종 약 79배 개선** (warm 기준). 실제 서비스는 warm 상태가 지배적이므로 warm 수치가 사용자 체감에 가깝다. Execution Plan도 완전히 인덱스 seek로 통합:

```
Index Scan Backward using idx_notification_requester_created
  Index Cond: (requester_id = 'svc-5' AND created_at 범위 
               AND ROW(created_at, id) < ROW(...))    ← 튜플 비교 전체가 Index Cond
```

`Incremental Sort` 노드도 사라짐. 인덱스가 `(requester_id, created_at, id)` lexicographic order이므로 `ORDER BY created_at DESC, id DESC`를 완전히 흡수. 커서 페이징이 **페이지 깊이와 무관하게 일정 latency**를 보이게 됨.

트레이드오프:
- 인덱스 크기 증가: id 8 bytes × 100만 row = 약 8 MB. 미미
- 쓰기 오버헤드: id는 이미 PK로 매 insert마다 생성되니 추가 부담 없음. B-Tree 노드 하나 갱신하는 비용
- 이득 대비 매우 저렴

### 관측 3: 조합 조회의 optimizer 판단 (F)

**쿼리**: `WHERE requester_id = 'svc-5' AND receiver = 'user-1234@example.com'`

**후보 인덱스 두 개** 중 optimizer가 알아서 선택:
- `idx_notification_requester_created (requester_id, created_at)`
- `idx_notification_receiver_created (receiver, created_at)`

**Optimizer가 하는 판단** (통계 기반):
- `requester_id = 'svc-5'` → 예상 매칭 약 50000 row (100만 / 20 서비스)
- `receiver = 'user-1234@example.com'` → 예상 매칭 약 10 row (100만 / 10만 사용자)
- 수신자가 5000배 좁음 → **receiver 인덱스 선택**

**실제 실행 결과**:
```
Index Scan Backward using idx_notification_receiver_created
  Index Cond: (receiver = '...' AND created_at 범위)
  Filter: (requester_id = 'svc-5')     ← 나머지는 Row Filter
  Rows Removed by Filter: 4
Execution Time: 0.043 ms
```

수신자 인덱스가 이미 4 row로 좁혔기 때문에 requester_id Filter 오버헤드는 무시할 수준. **별도 복합 인덱스 `(receiver, requester_id, created_at)` 없이도 충분**.

**시사점**:
- Optimizer가 최신 통계(`ANALYZE`)만 가지고 있으면 조합 조건에서도 잘 판단
- 인덱스 하나 더 추가 → 쓰기 비용/스토리지 증가 → 이득 대비 손해가 큼
- 다만 조합 조건이 압도적으로 자주 쓰이고 requester × receiver 조합에서도 여전히 많은 row가 나오는 시나리오면 복합 인덱스 검토 (실제 부하 관측 후 결정)

### 관측 4: 상태/채널 필터의 Filter 오버헤드 (D, E)

요청자 인덱스로 좁힌 뒤에 상태/채널 조건이 Filter로 처리된다. 요청자 조건이 이미 인덱스 range로 좁혀주기 때문에 Filter 오버헤드는 무시할 수준(0.10 / 0.41 ms).

상태/채널 조회가 압도적으로 자주 쓰이지 않는 한 별도 인덱스 추가는 불필요. 만약 필요하면 `(requester_id, status, created_at)` 같은 복합 인덱스나 `WHERE status IN ('SENT','FAILED')` 같은 partial index 검토.

### 후속 개선 후보

1. **커서 페이징 깊은 페이지 성능 개선** — native query로 튜플 비교 도입 (100배 → 유사 수준 기대). 우선순위 높음
2. 상태/채널 조회 빈도가 높아지면 partial index 또는 복합 인덱스 검토
3. 인덱스가 커버하지 못하는 컬럼(title, content 등)을 응답에서 뺄 수 있으면 `INCLUDE`로 Index-Only Scan 유도 가능

## 5. 페이징 — offset 방식과 cursor 방식

### offset 기반

- 구현이 단순하고 이해하기 쉽다.
- 페이지 번호 UI에 잘 맞는다.
- 뒤 페이지로 갈수록 `OFFSET N`이 앞 N개를 실제로 훑고 버리는 비용을 낸다.
- "최근 7일" 범위 안에서 총 데이터가 크지 않다면 실용적으로 무해할 수 있다.

### cursor 기반

- 구현이 조금 더 복잡하다. 다음 페이지 기준으로 어떤 값을 쓰고, 어떻게 인코딩할지 결정해야 한다.
- 최신순 조회와 궁합이 좋다. `(created_at, id)` 튜플 커서 조건을 인덱스가 그대로 태워 준다.

  ```sql
  WHERE requester_id = ?
    AND created_at >= now() - interval '7 day'
    AND (created_at, id) < (?, ?)
  ORDER BY created_at DESC, id DESC
  LIMIT ?;
  ```

- **`(created_at, id)` 튜플로 커서를 잡는 이유**: `created_at`만으로는 정렬이 유일하지 않다. 벌크 등록이나 짧은 시차로 같은 밀리초에 여러 알림이 생성될 수 있고, 이 경우 `created_at`만으로 커서 조건을 만들면 페이지 경계에서 같은 시각의 row 중 일부가 다음 페이지에 안 오거나 중복해서 오는 문제가 생긴다. `id`를 tie-break 키로 함께 담아 정렬 순서가 항상 유일하게 결정되도록 한다.
- 페이지 사이에 삽입/삭제가 있어도 중복/누락이 안정적이다.
- 페이지 번호로 점프하는 UX에는 맞지 않는다.

### 판단

- 이번 조회 시나리오는 "요청자별 최근 7일 최신순"이라 cursor 방식이 자연스럽다.
- 관리자 화면에서 페이지 번호 UX가 반드시 필요하면 offset을 별도로 열어 두는 것도 가능하다.
- 결정을 미루더라도, 응답 형식을 처음부터 `{ items, nextCursor }` 형태로 잡아 두면 이후 내부 구현만 바꿀 수 있다.
- 어느 쪽을 고르든 "왜 이 방식을 선택했는지"를 함께 남긴다.

## 6. 사용자 노출 범위는 7일, 저장 데이터는 계속 누적된다

조회가 최근 7일만 다뤄도 테이블에는 데이터가 계속 쌓인다.

- 테이블 크기 증가
- 인덱스 유지 비용 증가 (쓰기 지연, 저장 공간)
- 백업/복구 부담 증가
- 오래된 데이터를 어떻게 다룰지에 대한 기준 부재

즉, 위 §3~§5의 인덱스/페이징 설계는 "누적을 관리하지 않으면 서서히 무너진다"는 전제 위에 있다.

## 7. 파티셔닝 vs 샤딩

### 파티셔닝 — 한 DB 안에서 큰 테이블을 논리적으로 나눔

- `created_at` 기준 range partition (일 또는 주 단위)이 자연스럽다.
- 최근 7일 조회는 최근 파티션만 스캔하면 되므로 조회 비용이 안정적으로 유지된다.
- 오래된 파티션을 통째로 drop 하는 방식으로 아카이빙/삭제가 쉬워진다.
- 운영 복잡도가 낮아 이번 프로젝트 수준에서도 도입을 검토할 수 있다.

### 샤딩 — 여러 DB 인스턴스로 데이터 분산

- 라우팅, 분산 트랜잭션, 백업 정책 등 운영 복잡도가 크게 오른다.
- 트래픽/데이터 규모가 훨씬 크고, 단일 DB로 감당이 안 되는 시점에 검토한다.
- 이번 과제 범위를 넘는다.

### 이번 결론

- 지금 파티셔닝을 도입하지는 않는다.
- 다만 "언젠가 파티셔닝을 도입한다면 기준은 `created_at` 일 단위 range"라는 방향만 못 박아 둔다.
- 인덱스 설계도 이 방향에 어긋나지 않게 정렬 컬럼으로 `created_at`을 계속 살려 둔다.

## 8. 아카이빙

실무에서는 오래된 데이터를 메인 DB에 계속 두지 않는다.

- 최근 데이터 → 메인 DB
- 오래된 데이터 → 저비용 아카이빙 DB 또는 cold storage
- 트리거 조건은 "사용자 노출 범위(7일) + 운영 확인 여유"로 잡는다 (예: 30~90일 이후).

이 프로젝트에서는 후속 작업으로 남긴다. Outbox `PUBLISHED` 이벤트 정리 정책과 같은 축에서 함께 결정할 수 있다 (`docs/설계판단과고민.md` §4 참고).

## 9. 요구사항 이상의 기능은 이유를 함께 남긴다

기본 원칙은 **기능 양 늘리기 < 핵심 요구사항 정확히 구현**이다. 추가 기능은 필요할 때, 다음을 함께 남기고 도입한다.

- 어떤 인덱스가 함께 붙는가 + 컬럼 순서 이유
- 실행 계획이 어떻게 바뀌었는가 (Before / After)

후보 API:

- 요청자별 최근 7일 조회 (옵션 A: `requester_id` 컬럼 도입 전제)
- 상태 필터 조회 (`status` 기준)
- 수신자별 최근 7일 조회 (`receiver` 기준)

## 10. 구현 계획 (Phase별)

조회 API를 실제 도입하기로 결정한 경우를 가정한 계획 초안이다. 각 Phase는 별도 PR 단위로 잘라도 무방하다.

### Phase 0 — 조회 대상 컬럼 결정

- §2 옵션 A(`requester_id` 컬럼 추가) / B(수신자 기준 조회) / C(기존 컬럼만) 중 확정.
- A를 고르면 다음이 함께 필요하다.
  - `Notification`에 `requester_id` 컬럼 추가 마이그레이션 스크립트.
  - 신규 요청은 필수 필드, 과거 데이터는 backfill/기본값 방침 결정.
  - `도메인모델.md`와 `docs/요구사항.md` 갱신.
- 이 Phase가 확정되기 전에는 아래 Phase 인덱스/쿼리 예시의 컬럼 이름이 바뀔 수 있음을 전제로 둔다.

### Phase 1 — API 요청/응답 형식 (확정)

**엔드포인트**: `GET /notifications`

**쿼리 파라미터**

| 이름 | 타입 | 필수 | 기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `requesterId` | string | (아래 규칙) | — | 요청자 필터. `receiver`와 조합 가능 |
| `receiver` | string | (아래 규칙) | — | 수신자 필터. `requesterId`와 조합 가능 |
| `status` | string (콤마) | 선택 | 전체 | 상태 필터. 예: `status=SENT,FAILED`. 값은 `NotificationStatus` 열거값 |
| `channel` | string (콤마) | 선택 | 전체 | 채널 필터. 예: `channel=EMAIL,SMS`. 값은 `NotificationChannel` 열거값 |
| `from` | ISO-8601 datetime | 선택 | `now - 7일` | 조회 시작 시각 (`created_at` 기준, 포함) |
| `to` | ISO-8601 datetime | 선택 | `now` | 조회 종료 시각 (`created_at` 기준, 제외) |
| `cursor` | string | 선택 | — | 다음 페이지 조회 기준. 클라이언트는 서버가 응답에 넣어 준 값을 그대로 전달 |
| `limit` | int | 선택 | `20` | 페이지 크기. 최대 `100` |

- 필터 최소 요건: `requesterId`와 `receiver` 중 **최소 하나는 필수**. 둘 다 없으면 대량 스캔 위험이라 막는다.
- 두 값을 함께 지정하는 것도 허용. "특정 서비스가 특정 사용자에게 보낸 알림" 같은 조합 조회 유스케이스(마이페이지 서비스별 필터, CS 조사 등)에 대응하기 위해 배타 규칙을 두지 않는다.
- 둘 다 있는 경우 인덱스는 `(requesterId, createdAt)` / `(receiver, createdAt)` 중 optimizer가 카디널리티에 따라 선택하고 나머지는 filter로 처리된다. 실제 부하 테스트에서 이 케이스가 병목이면 복합 인덱스(`(receiver, requesterId, createdAt)` 등) 추가를 검토.

**응답 (200 OK)**

```json
{
  "items": [
    {
      "id": 1234,
      "requestId": "req-001",
      "requesterId": "order-service",
      "receiver": "user@example.com",
      "channel": "EMAIL",
      "status": "SENT",
      "title": "welcome",
      "createdAt": "2026-08-01T12:34:56"
    }
  ],
  "nextCursor": "eyJjcmVhdGVkQXQiOiIyMDI2LTA4LTAxVDEyOjM0OjU2IiwiaWQiOjEyMzR9"
}
```

- `content`는 응답에서 제외한다 (큰 데이터, 필요 시 상세 조회 API로 별도).
- `nextCursor`는 마지막 아이템의 `(createdAt, id)`를 인코딩해 만든다. 다음 페이지가 없으면 `null`.

**커서 인코딩**

- `base64url(JSON({"createdAt": createdAt-iso, "id": id}))`.
- 서버 내부의 정렬 기준을 문자열로 감싼 값이다. `NotificationSearchCursor` record를 Jackson으로 직렬화한다.
- 클라이언트는 값을 해석하지 않고, 다음 페이지 요청 때 그대로 다시 보낸다.
- 인코딩 방식이 바뀌어도 요청 파라미터 이름과 응답 형식은 유지한다.

**에러 응답 (400 ProblemDetail)**

기존 예외 핸들러 형식(`status`, `detail`, `timestamp`, `exception`)을 그대로 사용한다.

- `requesterId`와 `receiver`가 동시에 있거나 둘 다 없음 → "요청자 또는 수신자 중 정확히 하나를 지정해야 합니다"
- `limit`이 `1..100` 범위를 벗어남
- `cursor` 파싱 실패
- `from`/`to`가 파싱 불가능한 형식

### Phase 2 — 인덱스 초안

- 핵심 인덱스: `(requester_id, created_at DESC)`.
- 상태 필터가 조회마다 붙는다면 추가: `(requester_id, status, created_at DESC)`.
- PostgreSQL 추가 고려사항 (§3 참고)
  - Index-Only Scan을 노린다면 `INCLUDE (status, channel, receiver)`를 붙여 heap fetch를 없앤다.
  - 특정 상태만 자주 조회하면 partial index 후보(예: `WHERE status IN ('SENT','FAILED')`).
- 인덱스는 JPA 엔티티 `@Table(indexes = ...)`로 선언하고, 생성 DDL을 그대로 문서에 남긴다.

### Phase 3 — Repository / Query 구현

- QueryDSL 또는 Spring Data JPA로 커서 조건을 구현.

  ```sql
  SELECT ...
    FROM notification
   WHERE requester_id = :requesterId
     AND created_at >= :from AND created_at < :to
     AND (created_at, id) < (:cursorCreatedAt, :cursorId)
   ORDER BY created_at DESC, id DESC
   LIMIT :limit;
  ```

- 응답 매핑에서 `nextCursor`는 마지막 아이템의 `(createdAt, id)`를 인코딩해 채운다.
- 헥사고날 경계 유지: Controller → provided port(조회 유스케이스) → Application Service → required port(Repository).

### Phase 4 — EXPLAIN 및 부하 테스트

- 로컬 Postgres에 최근 7일치 대량 데이터를 주입한다 (예: 요청자당 10만 건).
- 인덱스 추가 **전/후** `EXPLAIN (ANALYZE, BUFFERS)`를 각각 캡처한다.
- 확인 포인트
  - `Index Scan` 또는 `Index Only Scan`이 실제 사용되는가
  - Index Only Scan이라면 `Heap Fetches: 0`인가
  - `Sort` 노드가 사라졌는가
  - 앞 페이지와 뒤 페이지의 커서 조회 응답 시간이 유의미하게 벌어지지 않는가
- k6 부하 시나리오는 기존 `perf/` 폴더 컨벤션을 따라 조회용 스크립트를 추가한다.

### Phase 5 — 문서 반영

- 실험 결과는 `docs/성능측정/실험-07-조회.md` 형태로 남긴다 (Before / After 실행 계획, k6 지표 포함).
- 최종 결정된 인덱스 목록과 근거는 이 문서 §3에 역으로 반영한다.
- `구현계획.md`가 이 시점의 구현 순서/범위를 반영하도록 갱신한다.

## 11. 정리 — 지금 결정할 것 vs 나중에 결정해도 될 것

**지금 결정하면 좋은 것**

- 조회 시나리오 중 어느 것을 "핵심"으로 둘 것인지 (§2)
- 페이징 방식 (offset / cursor) 과 응답 스키마 (§5)
- 조회 API 도입 시 함께 붙일 복합 인덱스 후보와 컬럼 순서 근거 (§3)
- 조회 API를 추가할 때 남길 문서 항목 (§9)

**미뤄도 되는 것**

- 파티셔닝 실제 적용 (§7)
- 아카이빙 DB 분리 (§8)
- 샤딩 (§7)

문서를 남기는 목적은 "지금 안 하기로 한 것"에도 이유가 있음을 기록해 두는 데 있다. 이 문서가 그 역할을 한다.
